◆ 為什麼需要這套治理

痛點不是「模型不夠強」，而是「沒有約束的 agent 會自我合理化、文件會互相矛盾、失效會無聲」。

模型每天都在變

Go／Zen／NIM 三個池、19 個 alias，可用性天天漂移。8 天內 default 模型被改了 5 次，全靠「文件跟不上實況」。

agent 會繞過規則

某個 agent 在 fallback 撞 429 時，直接改掉整個 hermes 的預設模型。威脅模型不是「它不懂」，是「它會自我合理化」。

失效是無聲的

檔案「看起來存在」但內容早就過時。一次架構審查抓出 12 處可查證的矛盾，其中 4 處直接誤導派工判斷。

◆ 核心設計：四塊基石

不依賴「記性」，而是靠機制讓系統可預測、可回滾、可驗證。

程序憲法 (agentos-constitution)

  • 三級授權 T1／T2／T3：做錯的代價決定層級
  • 防漂移閘門：會簽綁對象、回滾限縮、逾期自動 rollback
  • 最終監督者永遠是「人」

單一事實來源 (STATE.md + git)

  • 模型現況只有一個權威檔，其餘全部降級成指針
  • checker 跑三類回歸測試：alias 比對、路徑存在性、幽靈模型掃描
  • Obsidian 只當唯讀備查快照

分層派工 (T0–T3)

  • 決策層（T0）人親自；執行層（T2/T3）用便宜模型
  • 付費買決策、免費跑執行
  • 驗收條件必須可獨立重跑，否則不下放

多模型交叉審查 (red-team)

  • 請第三方模型（OX alpha、N550）紅隊審查自己的架構
  • 一石二鳥：測模型能力 ＋ 測架構自洽
  • 共識／分歧／獨有洞見三方交叉比對

◆ 常駐自動化：19 個 cron 在跑

這些是「人不在電腦前，系統照樣運作」的證明——不是 demo，是每天都實際執行的 production workflow。

◆ 一次完整的紅隊審查 loop

請第三方模型審查自己的架構，再把它的發現收斂落地——這整套本身就是一個可複用的治理動作。

OX alpha 審查 7 題 → 抓出 12 處矛盾 → 事實收斂（唯一權威檔） → 憲法瘦身 148→58 行 → 安全封堵（key 輪換＋hook＋權限）

交叉對比的價值

N550 負責「結構更清楚」（決策權矩陣表、職能對應欄），OX alpha 負責「防繞過機制不能砍」（它讀過原憲法，知道哪些閘門是核心）。兩者互補，我再綜合落地。

抓到的典型問題

  • 「歷史快照」殭屍段落會被 agent 復活引用
  • checker 檢查的是「舊規則」，規則改了它沒跟上（hollow 化）
  • 瘦身草案順手引入了未驗證的新流程

◆ 三個工程故事（面試能講的那種）

這些不是「我用了某個工具」，而是「我踩過坑、歸因、然後把教訓變成可執行規則」。

01 Incident Postmortem：八小時六件事故，只有一件是模型問題

某天系統出了六件事故，逐件歸因後發現：5 件是設定漂移／文件矛盾／失效無聲，只有 1 件是模型品質問題。結論是「框架本身正確，換框架只會把這五件事重來一次」——於是定下「框架鎖定、只換 LLM」的決策。這是標準的 SRE postmortem 思維。

02 Cost Governance：$10/月怎麼養一套 24/7 agent

把成本拆開算：Go 訂閱 $10 ≈ 90M output tokens（離峰價），官方直連同樣 $10 只有 15.2M——訂閱贏 6 倍。策略是「付費池跑決策、免費池跑執行、離峰半價跑批次、免費池當煞車」。會自己觸發自己的常駐 agent，一律掛免費額度當煞車。

03 多模型路由：清單有列 ≠ 叫得動

實測發現 opencode models 列出的模型有三個已 EOL（呼叫回 HTTP 410）。所以「推薦任何模型前先跑 5-token probe 看真實輸出，grep 清單是查字典不是驗證」。加上 fallback 三層鏈（Go 燒光 → 官方 → Zen → NIM），讓系統在模型池掛掉時自動降級，全程不需人為切換。
